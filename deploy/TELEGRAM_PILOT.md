# Пилот SQLite + Telegram

Google Sheets не требуется. Основное состояние — SQLite на постоянном volume.
Одна реплика worker. Codex используется для разработки и конечных тестов, не хостинга.

1. Подготовить Linux-хост с Docker Compose либо Railway background service.
2. Скопировать examples/config.json в игнорируемый config.json; sheets_write=false.
   Задать проверенные Telegram ID. Boss — руководитель, а test_operator — только
   согласованный тестовый получатель, если используется отдельный тестовый аккаунт.
   Имя/ID сотрудника нельзя угадывать по порядку участников или никнейму.
3. Указать business_account_user_id именно подключённого Business-аккаунта.
   Разрешить в Telegram Read Messages и Reply to Messages в выбранных чатах.
   Обычный бот (/start) нужен как резервный канал за пределами окна Business 24 часа.
4. Начать с review_mode=true: новые поручения становятся черновиками и направляются
   руководителю одной сводкой. Относительные сроки остаются неизвестными.
   speaker_aliases связывает подтверждённые метки стенограммы с ключами сотрудников.
   Неизвестный Speaker 2 остаётся без назначения. Модель ссылается на номера строк;
   программа сама сохраняет точные цитаты. Чужие инструкции в тексте не исполняются.
5. Для живого теста добавить allowed_live_recipients:["test_operator"] (или ["boss"]
   при проверке в личном чате руководителя с обычным ботом). Установить
   recipients_verified=true и live_send=true после проверки конкретного получателя.
   Остальные адресаты блокируются, даже если у них зарегистрирован чат.
6. Подключить настоящие токены через секреты хостинга. Proxy-placeholder облака
   нельзя переносить на другой сервер как настоящий ключ. Не извлекать и не копировать
   значения из облачной среды. В Compose создать .env вручную вне Git, права 600.
7. config.json должен читаться UID 10001. В нём только настройки и ID, без ключей;
   для локального Compose можно дать ему права 644. Volume должен быть доступен UID 10001.
8. docker compose -f deploy/compose.telegram.yaml build
   docker compose -f deploy/compose.telegram.yaml up -d
   docker compose -f deploy/compose.telegram.yaml logs --tail=100
   Сначала worker запускается только на тестовых получателях. Не запускать одновременно
   второй worker, reference_pilot или webhook для того же бота.
9. Прислать /start обычному боту. Загрузить планёрку текстом/UTF-8 .txt; допустимо
   до 32000 символов, файл до 64 KB. Просмотреть черновики и ответить с ID задачи:
   «Подтверждаю [ID], отвечаю я, срок 2026-10-20» либо указать подтверждённое имя сотрудника.
   Повторная планёрка не создаёт события/задачи заново и не вызывает модель.
10. Ответы сотрудника связываются через reply-to, ID или единственную активную задачу.
    Несколько задач без указания нужной → уточнение. /summary показывает сводку.
    «Почти готово» не завершает работу; нужен конкретный результат.

Проверка процесса: goldway ... health проверяет heartbeat, не доставку сообщений.
Docker unhealthy сам по себе не перезапускает контейнер; нужен внешний мониторинг.
Наблюдайте также события failed и outbox unknown/blocked через goldway ... status.
Unknown отправки вручную сверять в чате и использовать resolve-delivery, без слепых повторов.

Резервное копирование без остановки worker:
docker compose -f deploy/compose.telegram.yaml exec goldway goldway --config /run/config.json --db /data/goldway.sqlite backup /data/backups/YYYY-MM-DD.sqlite

backup использует SQLite backup API, включает WAL-состояние и проверяет целостность.
Указанный файл не должен уже существовать. Выгружать резервные копии с volume на
отдельное защищённое хранилище. Хранение только на том же диске не защищает от его потери.
Восстановление проверять на отдельной базе, не перезаписывая живую.

Railway: Dockerfile, одна реплика, volume /data. Config — /data/config.json; start command:
goldway --config /data/config.json --db /data/goldway.sqlite run
Подготовить файл/права через доступ к сервису. Если используется root-owned volume,
проверить доступ UID 10001 перед запуском. Public domain/HTTP healthcheck не нужен.
Секреты добавляются в Railway, а не в репозиторий. Серверный аккаунт ещё не подключён.

Краткий облачный тест worker: goldway ... run --run-seconds 60. Это конечная проверка,
не постоянный запуск. После окончания worker прекращает polling. Не запускайте
его, пока на сервере работает другой polling-процесс для того же бота.


Рабочая группа:
- В config указать meeting_recipient=meeting_group и allowed_group_ids с проверенным
  ID группы; разрешить meeting_group в proactive allowlist.
- Для адресата задать group_destinations: {"meeting_group":{"chat_id":"проверенный ID",
  "message_thread_id":null}}. При запуске запись автоматически появится в свежей SQLite.
  General — null; другая тема — подтверждённый положительный ID. Не угадывать ID по имени группы.
- Настройка группы не даёт ролей всем участникам автоматически. /start в личке бота
  регистрирует запрос, затем руководитель подтверждает сотрудника и Telegram ID.
- Новая сводка: HTML-карточки, постоянные номера №1, №2…, три карточки на сообщение.
- Свободное общение не меняет задачи. Для изменения нужно понятное поручение/результат
  по существующей доступной задаче. Реплики обычного группового обсуждения игнорируются.
