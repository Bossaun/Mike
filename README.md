# Помощник GOLDWAY — пилот

**Текущий режим: SQLite + Telegram. Google Sheets необязательна и выключена.**
Для запуска без таблицы см. [deploy/TELEGRAM_PILOT.md](deploy/TELEGRAM_PILOT.md).

Новая реализация на Python 3.11+, созданная в облаке без доступа к прежнему пакету
`GOLDWAY_telegram_pilot` на MacBook. 14.10.2026 получен отдельный архив аудита: его 63 исходных теста проверены,
исправленная копия с 69 тестами находится в `reference_pilot/`. По его AUDIT.md
это ещё один новый командный кандидат, а не восстановленный прежний пилот.
Репозиторий первоначально не содержал коммитов. Эти файлы не отправлялись в GitHub.

## Что реализовано

Один процесс: long polling Telegram → сохранённые события → JSON-действия модели →
проверка → SQLite → очередь Telegram и проекция Google Sheets. Без агентов и браузера.

SQLite — основное состояние: задачи, источники, обработанные события, Telegram offset,
маршруты, очередь, журнал доставки, итоги диалогов и расход модели. WAL и транзакции
сохраняют состояние после перезапуска. Для пилота с одним процессом это проще
PostgreSQL; база должна находиться на постоянном диске. Каждый бизнес использует
отдельную базу, конфигурацию, бота, таблицу и секреты. Сейчас включён только GOLDWAY.
Протокол `Model.propose(context)` позволяет менять провайдера без изменения управления
задачами. Поддержаны OpenAI, Anthropic и совместимый с OpenAI API через `base_url`.
Продажи и Instagram позже смогут добавлять события; склад, финансы и оплаты не меняются.

Модель получает новое событие, до 12 релевантных задач и 3 кратких итога переписки.
Программа проверяет владельца, ISO-даты, цитаты из источника, доступ к задаче,
статусы и ограничения. Отсутствующие сроки и ответственные остаются неизвестными.
Относительные сроки требуют уточнения в формате YYYY-MM-DD. Предложения получают
статус `proposed`; подтверждать их может руководитель. «Почти готово» не завершает
задачу. Для завершения нужен конкретный результат в новом сообщении.

Есть защита от повторного транскрипта (нормализованный SHA-256), повторного события,
задачи с тем же нормализованным названием и исходящих сообщений по ключу действия.
Семантическое сопоставление названий выполняет модель; произвольные перефразирования
не имеют гарантии отсутствия дублей. Ответ привязывается к задаче через reply-to,
ID/название или единственную активную задачу сотрудника. При неоднозначности бот
просит уточнить ID. Задачи модели вне разрешённого контекста отклоняются.

Проверка интервала напоминаний учитывает последний ответ. Напоминания создаются
не чаще `reminder_hours`; каждое имеет собственный ключ. При ответе ожидающие
сообщения по этой задаче данному сотруднику отменяются. Ежедневная сводка и `/summary`
показывают выполненное, просроченное и требующее решения.

## Локальная установка и проверка

```bash
cd /workspace/Mike
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m pip install -e '.[test]'
.venv/bin/python -m pytest -q
.venv/bin/goldway --config examples/config.json --db /tmp/goldway-demo.sqlite ingest examples/meeting.txt --fixture examples/actions.json
.venv/bin/goldway --config examples/config.json --db /tmp/goldway-demo.sqlite status
```

Повторите `ingest`: останется одна задача, одно обработанное событие и одно сообщение.
`--fixture` — явно заданный искусственный ответ модели, не реальный разбор текста.
Тест полного цикла использует реальные обработчики и SQLite с имитацией внешних API.
Никакие тесты не отправляют сообщения сотрудникам и не меняют вашу таблицу.
`requirements.lock` фиксирует все установленные runtime-зависимости.

## Подключение Telegram

1. Создать бота через BotFather и включить Business Mode. Подключить к нужному
   Business-аккаунту, разрешив только согласованные личные чаты и необходимые права.
2. Скопировать `examples/config.json` в игнорируемый `config.json`. Указать реальные
   Telegram user ID руководителя и сотрудников, ID Business-аккаунта и групп.
   ID нельзя угадывать по имени пользователя. Сверить роли Алена и Насти.
3. Каждый сотрудник и руководитель должен начать диалог с обычным ботом (`/start`).
   Это резервный канал. Для группы заранее согласовать состав и ID группы, добавить
   бота и проверить право писать; для свободных сообщений нужно отключить privacy
   mode либо дать боту подходящие права администратора. Подключение Business не
   предоставляет автоматически историю сообщений.
4. Передать `TELEGRAM_BOT_TOKEN` и `MODEL_API_KEY` через секреты среды/хостинга.
   Не помещать их в Git или текст конфигурации. Домен ключа модели должен соответствовать
   провайдеру. Цены в примере конфигурации — настройки, их необходимо сверить с тарифом.
5. Проверить `getMe`, `getBusinessConnection`, ID получателей и разрешённые чаты
   на тестовом аккаунте. Сначала оставить `live_send=false`, `sheets_write=false`.
6. После проверки поставить `recipients_verified=true`, затем `live_send=true`.

Актуальная документация просмотрена 14 октября 2026:
[Business bots](https://core.telegram.org/bots/features#business-bots),
[BusinessBotRights](https://core.telegram.org/bots/api#businessbotrights),
[getBusinessConnection](https://core.telegram.org/bots/api#getbusinessconnection).
`can_reply` разрешает отправку/редактирование в личных чатах с входящим сообщением
за последние 24 часа. Перед каждой отправкой Business сервис проверяет актуальное
подключение, `rights.can_reply`, правильный аккаунт и время входящего сообщения.
Вне окна выбирается обычный бот, с которым сотрудник начал диалог, либо разрешённая
группа с проверкой членства/прав. Если канала нет, сообщение остаётся `blocked`.
Получатели групп должны быть проверены заранее; конфиденциальность группы зависит от её состава.

Обрабатываются `business_connection`, `business_message`,
`edited_business_message`, `deleted_business_messages`, обычные сообщения и правки.
Собственные исходящие сообщения Business-аккаунта и сообщения ботов не обрабатываются.
Правка заменяет ещё не обработанное событие; удаление отменяет его. Если прежняя версия
уже изменила задачу, руководителю отправляется уведомление о необходимости сверки:
автоматически отменять последствия переписки небезопасно. История событий сохраняется.

Руководитель отправляет обычный текст планёрки, `/meeting текст` или UTF-8 `.txt`.
Лимит текста — 32000 символов; длинные встречи нужно разделить явно. PDF/DOCX/аудио
в этом этапе не поддержаны. Ответ сотрудника — обычный текст, предпочтительно reply
на вопрос бота. Руководитель подтверждает предложение ответом на сообщение с его ID.

Первоначальная история: отдельно экспортировать доступные транскрипты в UTF-8 `.txt`
и загрузить через `ingest` или бота. Импорт старых произвольных чатов не реализован:
его формат и полномочия нужно согласовать отдельно. Импорт не открывает 24-часовое окно.

## Google Sheets

В первой версии используйте **отдельную пилотную таблицу**, не основную рабочую.
Ожидаемые вкладки: `Задачи_GOLDWAY`, `Ален_день`, `Касания_GOLDWAY`.
Перед подключением нужно прочитать текущие заголовки и данные. Схема новой проекции:

| Колонка | Содержание |
|---|---|
| A | ID задачи (защищённая колонка) |
| B | Название |
| C | Ключ сотрудника: `alen`, `nastya`, … |
| D | Срок YYYY-MM-DD или пусто |
| E | Следующий шаг |
| F | Критерий завершения |
| G | confirmed / proposed / in_progress / blocked / completed |
| H | Источник (защищённая колонка) |
| I | Версия (защищённая колонка) |
| J | Результат/цитата |

Заголовки должны точно соответствовать `goldway.sheets.HEADERS`. При другой структуре
сервис остановит синхронизацию этой таблицы, сохранив Telegram и SQLite. Нужна отдельная
миграция/импорт, а не автоматическая перезапись существующих данных.

Все строки читаются через `get_all_values()`, без ограничений 150/200. В этом этапе
запись в `Ален_день` и `Касания_GOLDWAY` не производится; есть неограниченный reader
для проверки существующих записей. Тест отдельно находит запись в строке 201.

Ручные правки импортируются через сравнение с предыдущим снимком. Если SQLite уже
изменился, пользователь изменил ID/источник/версию либо удалил строку, возникает
конфликт: данные не перезаписываются. Смотрите `audit`. Не добавляйте строки вручную
без согласованного импорта. Статус `completed` требует нового конкретного результата
в J. Редакторы таблицы считаются доверенными операторами; ограничьте их права и защитите
A/H/I. Прямой пересмотр владельца и сроков через таблицу допускается только после проверки.

Включить Sheets API, создать service account, предоставить ему доступ **только**
к пилотной таблице. На постоянном сервере хранить JSON-ключ как секретный файл:
`GOOGLE_SERVICE_ACCOUNT_FILE=/run/secrets/google-service-account.json`.
Это локальная подпись Google, поэтому требуется настоящий секретный файл, а не
proxy-placeholder. Для облачных интеграционных проб можно использовать краткоживущий
`GOOGLE_SHEETS_ACCESS_TOKEN` через proxy-secret к `sheets.googleapis.com`.
Автоматическое продление этого токена не реализовано; постоянный сервер использует файл.
Поставить ID таблицы, `sheet_verified=true`, `sheets_write=true` только после проверки.

## Серверный запуск

Облачный Codex — разработка и проверка, не постоянный хостинг бота.
Нужен Linux-сервер с Docker, доступом к Telegram/модели/Google и постоянным диском.
Один экземпляр worker; горизонтальное масштабирование с SQLite не поддерживается.

```bash
# На сервере, в каталоге проекта
cp examples/config.json config.json
mkdir -p secrets
# Заполнить config.json; секреты подключить через менеджер секретов хостинга.
# Для локального Compose допускается игнорируемый .env с правами 600.
docker compose build
docker compose up -d
docker compose logs --tail=100 goldway
docker compose exec goldway goldway --config /run/config.json --db /data/goldway.sqlite status
```

`.env` содержит `TELEGRAM_BOT_TOKEN`, `MODEL_API_KEY` и, при Sheets,
`GOOGLE_SERVICE_ACCOUNT_FILE`. Каталог `secrets` монтируется только для чтения.
Volume `goldway-data` сохраняет SQLite/WAL; не удалять его при обновлениях.
Контейнер работает от UID 10001, volume должен быть доступен этому UID.
Если Docker build не имеет сети, можно заранее скачать проверяемые через TLS пакеты:
`.venv/bin/python -m pip download -r requirements.lock -r requirements-build.txt -d wheelhouse`,
затем `docker build --build-arg PIP_NO_INDEX=1 -t goldway-pilot .`.
Wheels зависят от платформы и версии Python; в этой среде проверен Linux x86_64/Python 3.12.
Сетевое скачивание внутри Docker этой облачной среды не работает из-за DNS;
проверка контейнера использует этот автономный способ. Wheels игнорируются Git.
Секреты, транскрипты и база не входят в Docker build context.
Файлы конфигурации должны читаться UID 10001; секретный Google-файл
нужно предоставить этому UID с минимальными правами, не делать общедоступным.
Проверка `goldway ... health` проверяет свежий heartbeat worker, а не доставку внешних API.
Не используйте несколько polling-процессов и webhook одновременно.

Для Railway: Dockerfile и `railway.toml`, volume `/data`; конфигурация и секретный
Google-файл вне образа. Если конфигурация находится в volume, задать start command:
`goldway --config /data/config.json --db /data/goldway.sqlite run`.
Не включать HTTP healthcheck и public domain: сервис использует long polling.
Заранее подготовить `/data/config.json` с правами для UID 10001. Настройка Railway
в реальном аккаунте и внешний постоянный запуск ещё не проверены.

Резервное копирование: SQLite backup API на отдельный защищённый диск; копирование
только одного .sqlite во время работы без WAL небезопасно. Периодически проверяйте
восстановление. После обновления сохраняйте volume, затем проверяйте `status` и логи.

## Ошибки, неизвестная отправка и бюджет

`pending`, `sent`, `retry`, `failed`, `blocked`, `unknown`, `cancelled` — разные состояния.
429 можно повторить после указанной задержки. Сетевой timeout, 5xx или остановка между
отправкой и фиксацией результата → `unknown`: **автоматически не повторяется**.
Ошибка первого получателя не останавливает остальных. Доставка ровно один раз не
гарантируется. После сверки реального чата оператор использует:

```bash
goldway --config config.json --db state/goldway.sqlite resolve-delivery 123 sent --message-id 456
# Только если достоверно установлено, что сообщения не было:
goldway --config config.json --db state/goldway.sqlite resolve-delivery 123 not-sent
```

Сбой модели оставляет событие `failed` с диагностикой, не частичные задачи.
После исправления причины: `goldway ... retry-event EVENT_ID`. Автоматических
неограниченных повторов платных вызовов нет. Worker продолжает другие события.
Расход токенов пишется в `usage`. До вызова резервируется консервативная стоимость;
после ошибки резерв не освобождается, поскольку провайдер мог обработать запрос.
`daily_budget` — USD за скользящие 24 часа по настроенным ценам; это программный лимит,
не замена лимиту аккаунта провайдера. Задайте также лимит у провайдера.

цитаты или результата: сначала нужна тестовая встреча и ручная проверка поручений.


## Обновление после получения архива аудита

Основной сервис в `goldway/` поддерживает полный событийный цикл. Исправленная
командная копия в `reference_pilot/` сохраняет схему и правила из архива; см.
`reference_pilot/CHANGES.md`. Это два пакета с одним именем, поэтому их тесты запускаются
отдельными процессами из соответствующих каталогов. Второй worker не запускать.

Исходные заголовки `Задачи_GOLDWAY` из архива отличаются от схемы новой проекции.
Для первого переноса предусмотрен **явный task-only импорт**, который не меняет таблицу,
не отправляет сообщения и по умолчанию только показывает сводку:

```bash
.venv/bin/goldway --config examples/config.json --db state/pilot.sqlite import-tasks reviewed-tasks.json --source 'идентификатор проверенного экспорта'
# После проверки экспорта применить только в пилотную SQLite:
.venv/bin/goldway --config examples/config.json --db state/pilot.sqlite import-tasks reviewed-tasks.json --source 'идентификатор проверенного экспорта' --apply
```

JSON содержит массив строк только вкладки задач с первой строкой заголовков.
Повторный импорт из того же источника не создаёт задачи заново и не перезаписывает
последующие изменения. Даты ISO/DD.MM.YYYY принимаются явно, относительные — неизвестны.
Ответственный сопоставляется только по точному настроенному имени. Составные владельцы
вроде «Я + разработчик» требуют ручного решения. Старый статус «Выполнено» без
конкретного доказательства не переносится как подтверждённое завершение.
`audit` сохраняет исходные ID и вопросы для сверки. Не экспортировать Users/Пароль.

В AUDIT.md сообщается о возможных паролях в основной книге; это здесь не подтверждено.
Для пилота нужна отдельная книга с рабочими данными, без этой вкладки. Доступ Google
пока не настроен, действительная структура/состав основной таблицы неизвестны.

Реальная проверка модели: ключ доступен, GET /v1/models возвращает 200,
`gpt-4.1-mini` доступна. Генерация возвращает HTTP 429 `credit_balance_exhausted`.
После пополнения баланса генерация успешно перепроверена: одна искусственная
планёрка → одна подтверждённая задача, 446 входных/142 выходных токена.
Повторная загрузка не вызывает модель. Подробности в VALIDATION.md.
Telegram getMe ранее успешен для @GOLDWAYCHAT_BOT и can_connect_to_business=true;
это не подтверждает подключение к Business-аккаунту или право писать сотрудникам.


## Проверка на реальной планёрке

В пилотном режиме review_mode=true новая встреча создаёт черновики предложений,
а не автоматически назначенные поручения. Руководитель получает одну сводку.
Для новых договорённостей, которые уже были явно назначены, при снятии review_mode
остаётся прежний режим confirmed; предложения модели остаются proposed.

В gpt-4.1-mini используется строгая JSON-схема. Модель ссылается на evidence_lines,
owner_lines, deadline_lines; программа проверяет номера строк и сохраняет цитаты
из оригинала. Для обновлений set_fields задаёт только изменённые поля, чтобы null
placeholders не стирали уже известного владельца/срок. Неподтверждённый владелец
черновика остаётся неизвестным с пометкой audit. OpenAI-совместимые провайдеры без
json_schema могут установить model.json_mode=true; проверки программы сохраняются.

Загруженная реальная планёрка: 9 черновиков, у 6 неизвестен ответственный,
у всех 9 нет точного срока. Speaker 2 пока не идентифицирован. Сводка действительно

## Рабочая группа и обычный диалог с ботом

meeting_recipient задаёт отдельный канал публикации (например meeting_group).
В chats этому получателю соответствует проверенный group_chat и, при необходимости,
group_thread_id. В General («Основной чат») message_thread_id не передаётся; для
другой темы нужно указать её подтверждённый ID. Групповые публикации выполняются
обычным ботом, без business_connection_id и без ограничения Business 24 часа.
Права группы проверяются перед отправкой. Подключение Business остаётся для личных чатов.

Сводки используют безопасную HTML-разметку и до трёх карточек в сообщении. Тексты
модели/сотрудников экранируются. У задач есть постоянный public_number в рамках бизнеса;
длинный внутренний ID показывать пользователю не нужно. «Задача №3» связывается с
существующей задачей и сохраняет ограничения роли. Номера не меняются после рестарта.

Ответ на обычное сообщение боту остаётся в диалоге с ботом. Ответ в разрешённой
группе остаётся в её теме. Для исходящих уведомлений без явного канала сохраняется
Business → обычный бот → разрешённая группа. Свободная беседа допускается без номера
задачи и не может изменять задачи: для conversation actions обязан быть пустым.
Реплики общего обсуждения в группе не считаются планёрками автоматически. Бот
реагирует на упоминание, reply ему, номер задачи, команды/запрос сводки или текстовый
файл планёрки от разрешённого администратора.

allow_onboarding_replies=true позволяет один ответ на /start новому личному пользователю:
он попадает в pending_members, без доступа к данным и без автоматического назначения
роли. Роль подтверждает руководитель, после чего Telegram ID вносится в конфигурацию.
allow_registered_replies=true допускает ответы уже подтверждённым сотрудникам в канале
их обращения; proactive allowlist всё ещё ограничивает плановые уведомления.
Бот не получает историческую переписку группы при добавлении.

Живой тест: найден GOLDWAY рабочий чат с forum=true, бот — administrator. 9 черновиков
опубликованы в General тремя сообщениями обычного бота, Telegram подтвердил отправки.
Приветствие и ответ на «А с тобой можно общаться?» отправлены в прямой диалог с ботом.
Краткий group worker test остановлен; постоянный хостинг по-прежнему отсутствует.
